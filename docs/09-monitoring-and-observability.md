# Phase 09 — Monitoring & Observability

## 1. Objective

The objective of this phase was to deploy a centralized monitoring infrastructure to observe the Ubuntu Server and its Docker containers.

The solution is built around five complementary components:

- **Prometheus:** collects and stores monitoring metrics.
- **Node Exporter:** exposes Linux host system metrics.
- **cAdvisor:** collects Docker container resource metrics.
- **Grafana:** visualizes metrics through dashboards.
- **Alertmanager:** receives and manages alerts generated by Prometheus.

The entire monitoring infrastructure is deployed using Docker Compose.

This phase introduces infrastructure monitoring, metrics collection, visualization and alert management.

## 2. Monitoring Architecture

### 2.1 Overview

```text
                       UBUNTU SERVER
                             |
                +------------+------------+
                |                         |
           NODE EXPORTER               cADVISOR
                |                         |
         Linux Host Metrics       Docker Container Metrics
                |                         |
                +------------+------------+
                             |
                         PROMETHEUS
                             |
                    Metrics Collection
                             |
                  +----------+----------+
                  |                     |
                GRAFANA            ALERTMANAGER
                  |                     |
              Dashboards          Alert Management
```

### 2.2 Component Roles

| Component | Role | Internal Port |
|---|---|---:|
| Prometheus | Metrics collection and storage | 9090 |
| Node Exporter | Linux system metrics | 9100 |
| cAdvisor | Docker container metrics | 8080 |
| Grafana | Metrics visualization | 3000 |
| Alertmanager | Alert management | 9093 |

The ports listed above are internal service ports.

For security reasons, only Grafana is published on the Ubuntu Server, bound to `127.0.0.1:3000`.

Prometheus, Node Exporter, cAdvisor and Alertmanager communicate through the internal Docker network without publishing their ports on the host.

Remote access to Grafana is provided through an SSH tunnel.

### 2.3 Monitoring Data Flow

The monitoring process follows these steps:

1. Node Exporter exposes metrics about the Linux host.
2. cAdvisor exposes metrics about Docker containers.
3. Prometheus periodically collects metrics from both exporters and from its own endpoint.
4. Grafana queries Prometheus to display metrics in dashboards.
5. Prometheus evaluates configured alerting rules.
6. When an alert condition is met, Prometheus sends the alert to Alertmanager for management.

Prometheus is responsible for evaluating the alerting rules. Alertmanager handles the resulting alerts, including grouping and notification routing.

## 5. Docker Compose Deployment

The infrastructure is defined in:

`/opt/stacks/monitoring/docker-compose.yml`

Five services are deployed:

- `node-exporter`
- `cadvisor`
- `prometheus`
- `grafana`
- `alertmanager`

### 5.1 Service Configuration

**Node Exporter**

Node Exporter exposes Linux system metrics.

It uses read-only mounts of the host's `/proc`, `/sys` and root filesystem to access host system information.

**cAdvisor**

cAdvisor collects resource usage metrics from Docker containers.

The current configuration uses elevated permissions through `privileged: true` and several host filesystem mounts.

This provides access to information required for container monitoring but increases the security impact of the container.

**Prometheus**

Prometheus collects metrics from the configured targets and stores them in a persistent Docker volume.

The retention period is configured to 15 days.

**Grafana**

Grafana visualizes the metrics collected by Prometheus.

A persistent volume is used to retain Grafana application data, including its configuration and dashboards.

**Alertmanager**

Alertmanager receives alerts generated by Prometheus and manages their grouping and notification routing.

A persistent volume is used to retain its state.

### 5.2 Docker Volumes

Three named persistent volumes are used:

- `prometheus_data`
- `grafana_data`
- `alertmanager_data`

These volumes preserve application data independently of the lifecycle of the containers.

Removing and recreating a container does not automatically remove its associated named volume.

However, persistent volumes are not a substitute for backups.

### 5.3 Docker Network

A dedicated Docker bridge network is used:

`monitoring-network`

All five services communicate through this network using Docker DNS and their service names.

This allows Grafana to reach Prometheus using its service name rather than a host IP address.

### 5.4 Port Publishing

Only Grafana publishes a port on the Ubuntu Server:

```yaml
ports:
  - "127.0.0.1:3000:3000"
```

This binds Grafana to the server's loopback interface.

Consequently, Grafana is not directly exposed through the server's external network interfaces.

The other monitoring services remain accessible through the internal Docker network without publishing their ports on the host.

## 6. Prometheus — Metrics Collection

Configuration file:

`/opt/stacks/monitoring/prometheus/prometheus.yml`

### 6.1 Global Parameters

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
```

- `scrape_interval`: frequency at which Prometheus collects metrics from its targets.
- `evaluation_interval`: frequency at which Prometheus evaluates alerting rules.

Both intervals are configured to 15 seconds.

### 6.2 Configured Targets

| Job | Target |
|---|---|
| prometheus | `prometheus:9090` |
| node-exporter | `node-exporter:9100` |
| cadvisor | `cadvisor:8080` |

Prometheus collects metrics from itself, the Linux host and Docker containers.

The targets are addressed using Docker service names because the services share the same Docker network.

### 6.3 Metrics Retention

The metrics retention period is configured to 15 days.

This allows historical metrics to remain available for dashboard visualization and monitoring analysis.

The retention period also helps control the amount of disk space used by Prometheus.

## 9. Grafana — Metrics Visualization

Grafana is used to visualize and analyze metrics collected by Prometheus.

### 9.1 Data Source Configuration

The Prometheus data source is configured automatically through Grafana provisioning.

File:

`grafana/provisioning/datasources/prometheus.yml`

Configuration:

```yaml
apiVersion: 1

datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    editable: true
```

The address `http://prometheus:9090` is used because Grafana and Prometheus communicate through the same Docker network.

The `proxy` access mode means Grafana queries Prometheus from the Grafana server side rather than requiring the user's browser to connect directly to Prometheus.

### 9.2 Dashboard Provisioning

The dashboard provider is defined in:

`grafana/provisioning/dashboards/dashboards.yml`

The directory configured to store dashboard files inside the Grafana container is:

`/var/lib/grafana/dashboards`

This provisioning mechanism allows Grafana to load dashboards from the configured directory.

## 10. Alerting — Prometheus and Alertmanager

An alerting system was configured to detect monitoring issues and resource utilization anomalies.

### 10.1 Alerting Rules

Configuration file:

`prometheus/rules/alerts.yml`

Three alerting rules are defined.

#### 1. TargetDown

```yaml
- alert: TargetDown
  expr: up == 0
  for: 1m
  labels:
    severity: critical
```

Detects a monitoring target that remains unavailable for at least one minute.

Prometheus uses the `up` metric to indicate whether a configured target was successfully scraped.

A value of `0` indicates that the target is unavailable.

#### 2. HighCPUUsage

```yaml
- alert: HighCPUUsage
  expr: |
    100 - (avg by (instance) (
      rate(node_cpu_seconds_total{mode="idle"}[5m])
    ) * 100) > 85
  for: 5m
  labels:
    severity: warning
```

Detects average CPU utilization above 85% for at least five minutes.

The expression calculates CPU usage from the rate of idle CPU time and groups the result by instance.

#### 3. HighMemoryUsage

```yaml
- alert: HighMemoryUsage
  expr: |
    (1 -
      node_memory_MemAvailable_bytes /
      node_memory_MemTotal_bytes
    ) * 100 > 90
  for: 5m
  labels:
    severity: warning
```

Detects memory utilization above 90% for at least five minutes.

The expression uses available memory rather than simply measuring unused memory.

### 10.2 Alertmanager Configuration

Configuration file:

`alertmanager/alertmanager.yml`

Alertmanager is configured to:

- Receive alerts from Prometheus.
- Group alerts by alert name.
- Wait 30 seconds before processing an alert group.
- Process subsequent group updates at five-minute intervals.
- Repeat notifications every four hours.

A receiver named `default-receiver` is defined.

However, no external notification system (email, Telegram, etc.) has been configured.

**Important:** Prometheus evaluates the alerting rules and sends resulting alerts to Alertmanager. Alertmanager manages those alerts, but external notifications are not yet configured.

The configured grouping and timing parameters do not, by themselves, mean that an external notification has been delivered.

## 11. Access to Monitoring Interfaces

For security reasons, Grafana is the only monitoring interface published on the Ubuntu Server.

Remote access from Linux Mint is provided through an SSH tunnel.

### 11.1 Grafana Access

From Linux Mint:

```bash
ssh -L 3000:127.0.0.1:3000 linux-server
```

The `linux-server` alias uses the SSH client configuration established during the initial infrastructure setup.

After opening the tunnel, access Grafana through:

`http://localhost:3000`

The SSH connection must remain active while using the tunnel.

### 11.2 Prometheus Access

Prometheus is not published on the Ubuntu host.

Its API and monitoring information can be inspected from inside the container using commands such as:

```bash
docker exec monitoring-prometheus wget -qO- \
'http://localhost:9090/api/v1/targets'
```

Prometheus is also accessible to Grafana through the internal Docker network.

A direct SSH tunnel to `127.0.0.1:9090` is not available with the current port configuration because Prometheus does not publish port 9090 on the host.

### 11.3 Grafana Initial Credentials

The initial administrator credentials configured for Grafana are:

- Username: `admin`
- Initial password: `admin`

The initial password must be changed during the first login.

Credentials and secrets must not be committed to the public Git repository.

## 14. Security Considerations

Several security measures were implemented:

- Grafana is bound to `127.0.0.1` and is not directly exposed through the server's external network interfaces.
- Remote Grafana access is provided through SSH.
- Prometheus, Alertmanager and the exporters do not publish host ports.
- Configuration files are mounted read-only where appropriate.
- Persistent application data is stored in dedicated Docker volumes.
- Internal service communication uses a dedicated Docker network.

### 14.1 Security Considerations for cAdvisor

The current cAdvisor configuration uses:

`privileged: true`

This grants the container extensive permissions on the host.

This configuration should be reviewed and hardened in a future security improvement.

### 14.2 Credentials and Secrets

The initial Grafana password must be changed.

Credentials, passwords, API tokens and other secrets must never be committed to the public Git repository.

A production deployment should also include appropriate access controls, backups and a review of container privileges.
